# 船舶即時位置查詢與地圖視覺化功能規格與技術評估報告

---

## 1. 業務需求與系統目標 (Business Requirements & Goals)

### 1.1 業務需求 (Business Need)
在現有 APP 中新增「船舶即時位置查詢」與「地圖視覺化」功能，使使用者能透過輸入船名（如 `Seri Alam`）或 IMO 編號（如 `9293832`），即時取得該 LNG 載運船之最新動態（包含當前座標、航速、航向、目的港、預計抵達時間與**位置最後更新時間**），並在地圖介面上精準定位與標註。

### 1.2 系統設計目標 (Design Goals)
* **低延遲與低成本**：將地圖渲染與標註作業完全移至 APP 前端地圖 SDK，LLM 僅負責自然語言解析與資料結構化，將單次查詢之模型請求次數控制為 1 次，大幅降低 Token 消耗。
* **數據精準性與時效透明**：由 App 後端直接對接專業 AIS 數據服務（如 MarineTraffic, VesselFinder API），避免大語言模型產生座標幻覺，並明確帶出位置更新時間以確保資料時效性。
* **架構優化**：透過前後端與 AI 模組的分工，確保系統能在高並發查詢下維持穩定運作與良好的使用者體驗。

## 3. 系統運作流程與架構 (System Architecture & Sequence Flow)

本系統採用 **「後端對接 AIS API + LLM 單次語意轉譯 + 前端 Direct 地圖 SDK 渲染」** 之高效能架構。

### 3.1 系統架構流程圖 (System Flow)

```
[使用者 UI] ──(1) 輸入船名/IMO──> [App 後端 API] ──(2) 查詢 AIS 數據──> [第三方 AIS API]
                                    │                                      │
[使用者 UI] <──(6) 渲染地圖 Marker──  │ <──(3) 回傳原始 JSON 數據 ────────────┘
     ▲                              │
     │                              ▼
 [前端地圖 SDK] <──(5) 回傳文字與座標── [App 後端] ──(4) Prompt + AIS 數據──> [LLM 模型]
```

### 3.2 詳細執行步驟 (Step-by-Step Execution)

| 步驟 (Step) | 執行主體 | 動作名稱 | 系統處理內容與說明 |
| :--- | :--- | :--- | :--- |
| **Step 1** | 使用者 / APP 前端 | 發起查詢 | 使用者於搜尋列輸入查詢指令（如：「查詢 Seri Alam 當前位置並在地圖顯示」）。 |
| **Step 2** | APP 後端 API | 呼叫 AIS 資料源 | 後端接收請求並解析參數，呼叫第三方 AIS API（如 MarineTraffic / VesselFinder API），取得即時航行數據（緯度、經度、航速、航向、目的港、**位置最後更新時間**等）。 |
| **Step 3** | APP 後端 API | 資料封裝與 Prompt 構建 | 後端將 AIS API 回傳之原始 JSON 資料打包，並組合 System Prompt 準備發送給 LLM。 |
| **Step 4** | LLM 模型 | 語意轉譯與 Payload 生成 | LLM 處理輸入後，生成繁體中文之自然語言狀態摘要（含時間說明），並同時輸出包含經緯度、時間資訊與 UI 控制參數之結構化 JSON 物件。 |
| **Step 5** | APP 前端 API Client | 接收回應 | APP 前端接收後端傳回之 LLM 摘要文字以及地圖標註所需之座標 Payload。 |
| **Step 6** | APP 前端地圖 SDK | 地圖打點與渲染 | APP 前端地圖元件（Google Maps SDK / Mapbox / Leaflet）讀取座標與最後更新時間，執行地圖聚焦 (`panTo`) 與 Marker 打點。**（此步驟無 LLM 參與， Token 消耗為 0）** |

## 4. LLM 資源消耗與成本評估 (Cost & Token Estimation)

### 4.1 模型請求次數與 Token 數據 (Per Query Metrics)

* **模型請求次數 (Model Request Count)**：**1 次 / 每次查詢**

| Token 種類 | 內容組成與範例 | 預估 Token 數量 |
| :--- | :--- | :--- |
| **Input Tokens (輸入端)** | • **System Prompt**：定義語意轉譯格式與 JSON 輸出規範（約 150~300 tokens）<br>• **User Input**：使用者對話與參數（約 15~30 tokens）<br>• **AIS Data Payload**：後端注入之原始航行數據與時間戳記 JSON（約 150~350 tokens） | **315 ~ 680 tokens** |
| **Output Tokens (輸出端)** | • **Summary Text**：繁體中文航行狀態摘要（含更新時間說明）（約 150~300 tokens）<br>• **Structured JSON**：地圖觸發數據 (`lat`, `lng`, `speed`, `last_updated_at`, `time_ago`, `zoom`)（約 60~120 tokens） | **210 ~ 420 tokens** |
| **總計 (Total Cost)** | **單次查詢 LLM 總 Token 消耗量** | **約 525 ~ 1,100 tokens** |

> **註**：地圖繪製與縮放由 Client 端地圖 SDK 處理，**地圖渲染部分之 LLM Token 消耗為 0**。

## 5. 數據格式規範 (Data & API Specifications)

### 5.1 LLM 輸出 JSON Payload 規範 (Output Schema)

為確保前端地圖 SDK 能正確解析並繪製 Marker 與顯示更新時間，LLM 必須嚴格輸出以下 JSON 結構：

```json
{
  "summary_text": "SERI ALAM (IMO: 9293832) 目前位於南海海域，航速 12.4 節，正駛往馬來西亞賓土路港 (Bintulu Port)。位置資料於 10 分鐘前更新。",
  "map_event": {
    "action": "RENDER_MARKER",
    "vessel_info": {
      "imo": 9293832,
      "name": "SERI ALAM",
      "type": "LNG Carrier",
      "latitude": 3.2145,
      "longitude": 113.0421,
      "course": 65,
      "speed": 12.4,
      "status": "Underway",
      "last_updated_at": "2026-07-31T14:17:34Z",
      "time_ago": "10 分鐘前"
    },
    "default_zoom": 8
  }
}
```

## 6. 團隊開發與架構討論議題 (Key Technical Discussion Topics)

1. **AIS 資料供應商選擇 (AIS Provider Selection)**：
   * 評估選用 MarineTraffic, VesselFinder 或 Spire 之 API 方案，比較其 Rate Limit、全球覆蓋率、位置資料更新頻率與訂閱費用。
2. **前端地圖 SDK 選型與 UI 展示 (Map SDK & UI Options)**：
   * 原生 iOS / Android 建議直接採用 **Google Maps Mobile SDK** 或 **Mapbox SDK**（套件編譯於 App 端，不佔用 GCP 容器空間）。
   * 前端地圖 Marker 彈出視窗 (InfoWindow) 或卡片需明確標示 `船名`,`位置更新時間：10 分鐘前` (`time_ago`)。
3. **後端快取與 Rate Limiting 策略 (Caching & Performance)**：
   * 同一艘船舶於 5~10 分鐘內的重複查詢，應於後端（Redis）建立 Cache 機制，避免產生重複的第三方 API 調用與 LLM Token 費用。
