## 2. 歷史回溯：2026-08-03 的故障原因與當初解法

經深入檢索專案歷史歸檔檔案 [`plan/2026-08-03/production_troubleshooting_2026-08-03.md`](file:///C:/Users/hilla/Desktop/opencode桌面/奶昔APP/plan/2026-08-03/production_troubleshooting_2026-08-03.md) 與 [`plan/2026-08-03/production_api_fix_2026-08-03.md`](file:///C:/Users/hilla/Desktop/opencode桌面/奶昔APP/plan/2026-08-03/production_api_fix_2026-08-03.md)，成功查明當初的故障與修改紀錄：

### 2.1 當初的原因 (2026-08-03 根因)
* **GAS 平台凌晨瞬時故障**：Google Apps Script 雲端平台在清晨偶發瞬時故障，後端定時排程呼叫 `SHIP_SCHEDULE_API_URL` 時遭遇 HTTP 404（或非 200 回應）。
* **拋出未捕獲異常**：原程式碼 `UrlFetchApp.fetch(SHIP_SCHEDULE_API_URL)` 預設在非 2xx 時會直接拋出 `Exception`。
* **靜默失敗與資料清空**：`catch (e)` 吞掉異常後，變數 `apiDataRaw` 保持為空字串，使船期解析結算為空陣列 `[]`，進而無防備地將線上 Firebase 船期表清空。

### 2.2 當初的解法 (2026-08-03 實作)
當初在 [`正式版/gs_NV4.7.7.js`](file:///C:/Users/hilla/Desktop/奶昔code_Q/正式版/gs_NV4.7.7.js#L3-L22) 標頭記錄了變更：
> `// *15. 2026/08/03 船期 API 呼叫全面加入 muteHttpExceptions 防護與 HTTP 狀態碼檢查，避免平台瞬時 404 導致靜默失敗。`
> `// *16. 2026/08/03 checkDailySchedule 加入排程結果摘要日誌，方便事後追查。`

具體修改了 3 處 API 呼叫點：
1. `checkDailySchedule()` (04:00 自動排程)
2. `getScheduleList()` (船期表抓取核心)
3. `doGet` 的 `set_mode` 結束分支 (隔天船期查詢)

將原本裸抓的代碼：
```javascript
const apiData = safeJsonParse(UrlFetchApp.fetch(SHIP_SCHEDULE_API_URL).getContentText());
```
改為加入 `{ muteHttpExceptions: true }` 並檢查狀態碼：
```javascript
const resp = UrlFetchApp.fetch(SHIP_SCHEDULE_API_URL, { muteHttpExceptions: true });
if (resp.getResponseCode() === 200) {
  apiDataRaw = resp.getContentText();
} else {
  console.error(`⚠️ getScheduleList 船期 API HTTP ${resp.getResponseCode()}`);
}
```

## 3. 根因剖析：為何昨天與今天再次復發？

比對目前工作區的主力測試版 [`gs_test.js`](file:///C:/Users/hilla/Desktop/opencode桌面/奶昔APP/gs_test.js) 與當初正式版的修改，發現了**兩大核心關鍵根因**：

### 根因一：當前主力版本 `gs_test.js` 遺漏了當初 08-03 的防護代碼（未同步）
當前 [`gs_test.js`](file:///C:/Users/hilla/Desktop/opencode桌面/奶昔APP/gs_test.js#L1145-L1155) 的 `getScheduleList()` 依然是舊的裸調用寫法：
```javascript
// ⚠️ 當前 gs_test.js 中的寫法：
let apiDataRaw = "";
if (SHIP_SCHEDULE_API_URL) {
  try {
    apiDataRaw = UrlFetchApp.fetch(SHIP_SCHEDULE_API_URL).getContentText(); // 💥 沒有 muteHttpExceptions！
  } catch (e) { console.error("抓取日曆 API 失敗: " + e); }
}
```
一旦 Google Apps Script 平台在清晨或排程執行時遭遇瞬時 404、500、或冷啟動超時，`UrlFetchApp.fetch` 直接拋出中斷 Exception，被 `catch` 吞掉後 `apiDataRaw` 即為空！

### 根因二：當初 08-03 的解法留有未解的架構漏洞 ——「缺少 Fail-Safe 保險機制」
即使加了 `{ muteHttpExceptions: true }`，如果 API 回傳 404/500，`apiDataRaw` 依然會是空字串，`mappedList` 依然會結算為空陣列 `[]`。
而 `updateFirebaseScheduleList()` 的邏輯是：
```javascript
function updateFirebaseScheduleList() {
  const list = getScheduleList(); // 拿到 []
  const res = callFirebase("schedule_list", list, "put"); // 💥 毫無檢查，直接抹除線上整張船期表！
}
```
**架構上缺少「寧可保留舊資料，絕不覆蓋空資料」的 Fail-Safe 保險機制**！

### 根因三：為何手動更改日曆活動日期能恢復？
在 [`gs_test.js`](file:///C:/Users/hilla/Desktop/opencode桌面/奶昔APP/gs_test.js#L1374-L1379) 中：
```javascript
function onCalendarOrSheetChange() {
  ensureTestEnvironment();
  console.log("📅 偵測到內容變更，啟動同步...");
  updateFirebaseScheduleList();
}
```
手動更改日曆活動會觸發 Google Calendar 的即時事件通知，重新調用 `updateFirebaseScheduleList()`。此時 API 平台連線正常，成功抓到未來船期並寫回 Firebase，因而恢復顯示。
