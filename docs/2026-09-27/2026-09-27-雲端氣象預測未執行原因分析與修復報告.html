⏱️ 2. 事件關鍵時間軸 (Causal Timeline)

12:15 (04:15 UTC)
第一輪掃描 — 耗時 114 秒
Cloud Scheduler 啟動更新，因空軍尚未發信，程式逐一輪詢並全量下載 252 封歷史郵件（含所有 .doc 附件），勉強在 114 秒結束並回報無信件。

因為網路波動與龐大資料傳輸，下載時間超過 Cloud Run 的 300 秒（5 分鐘）Timeout，前端 Proxy 返回 HTTP 504 Gateway Timeout。
12:35 關鍵致命點

超時中斷後，Cloud Run 立即將容器 CPU 限流凍結，後台線程被阻斷在網路等待中，無法執行到 finally: is_pipeline_running = False。標誌位被永久死鎖為 True！
13:36:46

13:45 ~ 17:45 (長達 4 小時)

每一次 Scheduler 發起請求，app.py 判斷 is_pipeline_running == True，於 2 毫秒內拒絕請求並回傳 429，導致即使信件已到，系統仍毫無動作。

🔬 3. 雙重根因剖析 (Root Cause)

根因一：IMAP 搜尋機制粗暴，無節制下載歷史郵件
原 src/email_receiver.py 使用 mail.fetch(msg_id, "(RFC822)") 遍歷寄件者全部 252 封信。在郵件未到時，會下載數十 MB 的歷史附件，耗時 2~5 分鐘，必定撞毀在 Cloud Run 300 秒逾時牆上。
根因二：執行防重入鎖缺乏 TTL 逾時自毀機制
is_pipeline_running 為純記憶體布林變數。在異常超時被雲端限流終止時，無法觸發清理回調。由於沒有逾時自動過期機制，導致整座容器陷入死結，直到手動注入 force 參數前無法自癒。

🛠️ 4. 永久防護修復措施 (Fixes & Diffs)

已針對上述兩個根因實施永久性優化：

(1) IMAP 輕量標頭預檢 + 深度截斷 (src/email_receiver.py)

  • 深度截斷：氣象預報必定為當日或近期寄出，強制限制只搜尋最新 15 封 郵件。
  • 標頭預檢：使用 BODY.PEEK[HEADER.FIELDS (SUBJECT)] 只讀取主旨（幾十 bytes），完全不下載大型附件。確認匹配才下載單一郵件。
  • 效果：郵件未到時的巡檢耗時從 >300 秒 驟降至 1.8 秒！
- for msg_id in reversed(message_ids):
-     status, msg_data = mail.fetch(msg_id, "(RFC822)")  # 全量下載整個信件與 .doc 附件
+ scan_list = list(reversed(message_ids))[:15]            # 截斷只查最新 15 封
+ for msg_id in scan_list:
+     status, header_data = mail.fetch(msg_id, "(BODY.PEEK[HEADER.FIELDS (SUBJECT)])") # 極速標頭預檢
+     # 命中目標主旨後，才針對該封執行完整 (RFC822) 下載

(2) 防重入鎖 300 秒 TTL 自動熔斷機制 (app.py)

  • 紀錄每次啟動的 pipeline_start_time。
  • 若鎖定狀態超過 300 秒（5 分鐘），判定為異常殘留並自動強制釋放鎖定，系統具備自動修復能力。
+ # 逾時死鎖防護：若上次執行超過 300 秒（5 分鐘），判定為異常殘留並強制重置
+ if is_pipeline_running and (time.time() - pipeline_start_time > 300):
+     print("[Warning] Pipeline lock expired (>300s). Auto-resetting lock.")
+     is_pipeline_running = False
