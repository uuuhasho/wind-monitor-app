# 2026-09-27 雲端氣象預測未執行原因分析與修復紀錄

## 1. 錯誤現象 (Symptom)
- **現象**：使用者反應今天（2026-09-27）APP 沒有天氣預測分析結果，畫面仍停留在 09-25 的舊預報資料。
- **排程狀態**：Cloud Scheduler (`forecast-trigger-test`) 設定每 15 分鐘（12:00～17:00）自動呼叫 Cloud Run `/update_forecast`。但自 12:45 起，所有呼叫皆失敗，日誌中回傳：
  ```json
  HTTP 429 {"status": "ignored", "msg": "Pipeline is already running"}
  ```
  在 Cloud Scheduler 端呈現 `RESOURCE_EXHAUSTED` (Status Code 8)，導致整天排程均未能成功取得並解析今日預報。

---

## 2. 根因分析 (Root Cause Analysis)

### 關鍵時間軸與因果鏈 (Timeline & Causal Chain)
1. **空軍預報郵件寄出時間**：
   今日預報郵件係於 **13:36:46 (+0800)** 始寄達 Gmail 收件匣。因此在 12:00 ~ 13:30 之間，Gmail 內確實尚未有 `0927` 的郵件。
2. **舊版 IMAP 全量下載瓶頸**：
   在 `src/email_receiver.py` 中，程式使用 `mail.search(None, f'(FROM "{target_sender}")')` 取得該寄件者全部 252 封歷史郵件，並在迴圈中對**每一封**郵件執行：
   ```python
   status, msg_data = mail.fetch(msg_id, "(RFC822)")
   ```
   `(RFC822)` 會下載完整郵件內容（含 `.doc` 龐大二進位附件）。當當日郵件尚未送達時，迴圈會依序下載所有 252 封歷史郵件，耗時長達 115 至 300+ 秒。
3. **12:30 觸發 Cloud Run 504 閘道超時**：
   在 12:30 的排程觸發中，下載耗時突破 Cloud Run 的 300 秒（5 分鐘）Timeout 上限，Cloud Run 前端閘道向客戶端回傳 `HTTP 504 Gateway Timeout`。
4. **CPU 凍結導致記憶體鎖死 (Zombie In-Memory Lock)**：
   Cloud Run 容器在 HTTP 請求超時中斷後，若無其他請求進入，其實例 CPU 配置會被立即限流凍結（Throttled to zero）。導致背景處理緒未能順利走完 `finally: with lock: is_pipeline_running = False`。
5. **後續排程全數遭遇 429 拒絕**：
   `is_pipeline_running` 為 Python 記憶體變數且缺乏過期時間（TTL）。因此自 12:45 起至 17:45，即便 13:36 郵件已寄達，後續每一次 Cloud Scheduler 請求一進入 `app.py` 即命中：
   ```python
   with lock:
       if is_pipeline_running and not force:
           return jsonify({"status": "ignored", "msg": "Pipeline is already running"}), 429
   ```
   全數於 2 毫秒內被拒絕，系統陷入永久死鎖。
