🔍 1. 為什麼 00Z 時間錯位會一直出現？（四重漏洞交織）

過去每當空軍發布 00Z（當日 00:00 UTC，台灣時間 08:00 起算） 之預報時，線上環境必定將起始時間誤判為 12Z（前一日 12:00 UTC，台灣時間 20:00），整整往過去平移了 12 小時。經過深度反編譯與線上日誌比對，根因如下：

漏洞一：跨平台設定錯誤 —— Linux 容器下的 Tesseract 被寫死為 Windows 路徑

代碼在 src/cv2_parser.py 原先包含 pytesseract.tesseract_cmd = r'C:\Program Files\Tesseract-OCR\tesseract.exe'。當代碼被打包部署至 Cloud Run（Debian Linux 容器）時，該指令無條件執行。由於 Linux 上根本不存在 C:\Program Files...，導致 Cloud Run 上的 OCR 在每次執行時皆拋出異常並靜默回傳空字串 ""，OCR 在線上全面癱瘓！

（Cloud Run 原始實體 Log 證實：[OCR Notice] Title regex did not match. Raw title text: ''）

漏洞二：舊版 Fallback 容錯機制「死鎖於 12Z」

當 OCR 癱瘓輸出空字串時，程式進入舊版 Fallback：first_hour = 12; if bottom_ocr_matches[0] == "00": first_hour = 0。因為底部時間軸 OCR 也一同癱瘓，bottom_ocr_matches 永遠為空，導致系統毫無例外一律猜測為前一天的 12Z！對於 12Z 的檔案（如 0926）恰好歪打正著，但只要遇到 00Z（如 0925），必定發生 12 小時嚴重錯位。

漏洞三：判斷架構順序顛倒 —— 時間推導在節點數計算「之前」執行

在氣象專業物理特徵中，00Z 預報必然為 23 點（5.5 天），12Z 預報必然為 33 點（8.0 天）。系統明明擁有「折線週期自相關演算法」，可以在不依賴任何文字的情況下 100% 精準分辨是 23 點還是 33 點（0925 自相關：23 點得分 +2630，33 點得分 -520）。但過去架構卻先執行時間猜測，後計算節點數，使得 Fallback 痛失這項關鍵物理 Ground Truth！

漏洞四：缺乏雲端原生視覺 AI (Gemini Vision) 備援

Cloud Run 已具備 Secret Manager 注入之 GEMINI_API_KEY，但在本地 Tesseract 遇到字符粘連或雜訊時，並未接入 Gemini 2.5 Flash Vision 作為二級 OCR 守護神。

🛡️ 2. 四重防禦立體架構（永久根治方案）

防禦層一：跨平台動態探測 (Linux 原生 Tesseract)

移除硬編碼路徑。系統動態識別 OS：Windows 下存在指定路徑時才指派；Linux 容器內自動綁定 /usr/bin/tesseract，確保 Cloud Run 容器內 Tesseract 原生 CLI 滿血復活。

防禦層二：輕量級 Gemini 2.5 Flash Vision 二級備援

實作 get_initial_time_via_gemini_vision，使用原生 requests + base64 調用 REST 端點。若 Tesseract 遇到文字辨識困難或空字串，0.6 秒內自動喚醒視覺 AI 辨識右上角標籤。

防禦層三：物理折線週期自相關提前判定 (Ground Truth)

將自相關（Autocorrelation）判定前置！只要紅線波形判定為 23 節點 (5.5 天)，即便在所有 OCR 徹底中斷的極端狀況下，物理規則亦強制鎖定為 00Z（當日 00:00 UTC），絕對不允許退回 12Z！

防禦層四：三方信號共識會審 (Consensus Voting)

標題 OCR（Tesseract / Gemini）、底部軸標籤（00 vs 12）與物理節點數（23 vs 33）進行交叉校驗。若判定為 00Z，強制作業點數必為 23 點；若為 12Z 則必為 33 點，確保點距與時序 100% 精準。
