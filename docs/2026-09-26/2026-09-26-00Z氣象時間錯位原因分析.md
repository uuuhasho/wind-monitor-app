# 2026-09-26 00Z 氣象時間錯位原因分析與永久修復

**記錄日期**：2026-09-26  
**問題描述**：空軍發布 00Z 起算之天氣預報時（例如 2026-09-25 發布之 `0925中油.doc`），線上 Cloud Run 管線解析出之時間為 `12Z24SEP`（台灣時間 2026-09-24 20:00），但原始圖檔右上角明確標記為 `00Z25SEP`（台灣時間 2026-09-25 08:00），整整發生 12 小時嚴重位移。且此 00Z 錯位現象頻繁出現。

---

## 一、錯誤現象 (Symptom)

1. **使用者遇到的症狀**：
   - 0925 分析結果與原始檔時間不同。
   - 0925 原始檔右上角標示為 `00Z`（`00Z25SEP initial field`），起算點為 25 日 08:00 CST。
   - 但系統寫入 Firebase RTDB 與圖表上的起始時間卻為 `2026-09-24T20:00:00+08:00`（即 `12Z24SEP`），整體時序往前平移了 12 小時。
   - 導致 Open-Meteo 逐時陣風數據與空軍風速折線發生 12 小時錯位，船舶進出港防風評估出現嚴重偏差。

2. **GCP Cloud Run (forecast-api-test) 實體日誌症狀**：
   ```text
   [OCR Notice] Title regex did not match. Raw title text: ''
   [OCR Bottom Axis] Found 0 intervals: [] ... 
   [Fallback Time] Inferred initial time: 12Z24SEP (first_hour=12Z)
   First record: {'timestamp': '2026-09-24T20:00:00+08:00', 'cpc_wind_speed': 1.79, 'open_meteo_wind_speed': 8.9}
   ```
   - 標題 OCR 提取字串為空字串 `''`。
   - 底部時間軸提取區間數為 `0`。
   - 觸發 Fallback 強制假設為前一日 12Z (`12Z24SEP`)。

---

## 二、根因分析 (Root Cause Analysis)

經過逐層排查，造成 00Z 錯位反覆出現的核心根因共有四點：

### 1. 跨平台環境差異：Linux 容器環境下 Tesseract 路徑被寫死為 Windows 路徑
在 `src/cv2_parser.py` 原第 9 行包含：
```python
# 確保 Windows Tesseract 路徑正確 (如果系統有安裝)
pytesseract.pytesseract.tesseract_cmd = r'C:\Program Files\Tesseract-OCR\tesseract.exe'
```
在本地 Windows 開發機上，雖然系統未安裝 Tesseract CLI，但因為 `TesseractCAPI` 成功載入了本機的 `tesseract50.dll`，因此本地測試皆能通過。  
然而，當代碼透過 Dockerfile 部署至 GCP Cloud Run（Debian Linux 容器）時：
- Linux 環境根本不存在 `.dll` 檔，導致 `TesseractCAPI` 初始化失敗返回 `None`。
- 程式隨後降級至 `pytesseract.image_to_string()`。
- 但此時 `pytesseract_cmd` 已被第 9 行強制覆寫為 `C:\Program Files\Tesseract-OCR\tesseract.exe`。
- Linux 容器內嘗試調用 Windows 實體路徑，直接拋出 `FileNotFoundError` 被 `except Exception: return ""` 靜默吞掉。
- **結果**：線上 Cloud Run 容器每次執行的 OCR 輸出結果 100% 為空字串 `""`，OCR 功能在雲端完全癱瘓！

### 2. 舊版 Fallback 容錯機制死鎖於「前一日 12Z」
舊版 Fallback 邏輯如下：
```python
first_hour = 12
if bottom_ocr_matches and bottom_ocr_matches[0] == "00":
    first_hour = 0
...
if first_hour == 0:
    initial_dt = target_dt.replace(hour=0, minute=0, second=0)
else:
    initial_dt = (target_dt - timedelta(days=1)).replace(hour=12, minute=0, second=0)
```
因為在 Cloud Run 上底部時間軸 OCR 同樣癱瘓，`bottom_ocr_matches` 永遠為空陣列 `[]`，導致 `first_hour` **無條件死鎖在 12**。當空軍發布 00Z（當日 00:00 起算）之圖表時，系統一律強制退回前一日 12Z，必然產生 12 小時的時間位移！

### 3. 邏輯順序架構缺陷：時間推算在節點數判定之前執行
在空軍氣象預報圖的物理特徵中：
- **00Z 預報（上午發布）**：必然為 **23 節點 (5.5 天)**，首點起算為當日 00:00 UTC。
- **12Z 預報（傍晚/夜間發布）**：必然為 **33 節點 (8.0 天)**，首點起算為前一日 12:00 UTC。

程式原先已具備紅線週期自相關演算法（Autocorrelation），可在不依賴任何文字 OCR 的情況下，透過折線波峰與波谷間距精準算出點數是 23 點還是 33 點（0925 自相關實測：23 點為 +2630，33 點為 -520）。但舊代碼將時間推算放在自相關計算「之前」，導致 Fallback 根本無法獲得節點數的物理先驗資訊！

### 4. 缺乏雲端原生視覺 AI 備援
Cloud Run 已具備 GCP Secret Manager 注入之 `GEMINI_API_KEY`，但當本地 OCR 遇到字體模糊或環境異常時，並未引入 Gemini 2.5 Flash Vision 進行高速二級備援。
