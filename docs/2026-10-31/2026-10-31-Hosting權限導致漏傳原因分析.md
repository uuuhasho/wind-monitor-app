# Hosting 發布漏傳與 404

日期：2026-10-31。狀態：已恢復並完成線上唯讀驗證。

## 現象

使用者授權 Hosting-only 發布後，Firebase CLI 回報 success，但版本 `8488a66a1198d119` 僅回報 2 檔、629 bytes；`/` 與 `/test` 皆 404。Cloud Run `/health` 仍為 200，RTDB 沒有改動。

## 根因證據

- `deploy/build_hosting.py` 以 Python `tempfile.mkdtemp()` 建立暫存樹，再把 site rename 成 `public/`。
- `public/` ACL 僅包含 OWNER RIGHTS、SYSTEM、Administrators；owner 為離線沙箱身分。建置身分能讀取檔案，不代表發布身分也能讀取。
- 網路／瀏覽驗證執行身分曾在讀取 `public/index.html` 時遇到 `EPERM`；Firebase 發布結果亦未包含網站首頁與大多數資產。原建置的檔案 hash 本身正確。
- 改用原生 PowerShell 建立的繼承權限暫存目錄後，同一發布身分可逐檔讀取 17 份網站產物；修復發布後來源、暫存與線上檔案 hash 全部一致。這些結果支持不同執行身分之 ACL 不相容是漏傳原因。

## 修復與命令差異

未修改原 `public/` ACL，也未複製任何機密設定；只把已建置網站內容複製到 `runtime/hosting-publish-2026-10-31/site/`。部署設定放在 site 外，保持原 headers、rewrites，public 精確指向該 site。

```diff
- firebase deploy --only hosting --project newlngship
+ firebase deploy --only hosting --project newlngship --config runtime/hosting-publish-2026-10-31/firebase.json
```

這是本次發布方式修復，沒有新增 APP 邏輯差異。原 `deploy/deploy_hosting.ps1` 未在本次改寫；再次部署必須先用實際發布身分驗證產物可讀，不可直接把不完整的 CLI success 當完成。
