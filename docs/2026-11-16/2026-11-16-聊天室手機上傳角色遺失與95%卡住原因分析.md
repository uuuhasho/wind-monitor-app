# 2026-11-16 聊天室手機上傳角色遺失與 95% 卡住原因分析

## 1. 錯誤現象
1. **手機選擇角色後上傳附件或拍照時跳出「請先選擇角色再上傳附件」**：
   - 使用者在聊天室選擇發言角色（如 `Pilot`）後，點擊附件並選擇「拍照」或「選擇檔案/相簿」，返回聊天室時上方出現紅色錯誤提示「請先選擇角色再上傳附件」，且畫面切回「觀眾模式」。
2. **圖片上傳進度條卡在 95%**：
   - 上傳圖片時進度條停在 `上傳中 95%` 不會自動消失；退出聊天室再重新進入後，圖片其實已成功送出並可正常點擊預覽。

## 2. 根因分析
1. **手機開啟相機 / 檔案選擇器導致 Firebase `onDisconnect().remove()` 觸發並清空席位**：
   - 領取角色席位時會在 RTDB 註冊 `wonRef.onDisconnect().remove()`。
   - 手機瀏覽器/PWA 開啟系統相機或檔案選擇器時，網頁會進入背景並可能遭作業系統暫停 WebSocket 連線，使 Firebase 伺服器觸發 `onDisconnect().remove()` 刪除 `seats/{seatKey}`。
   - 返回頁面後 `chatSeatsHandler` 發現遠端席位為 `null` 即呼叫 `handleRemoteSeatForfeit()` 將 `mySeat` 清空並切回觀眾模式；隨後 `<input type="file">` 的 `change` 事件觸發 `handleChatFileSelect()`，因 `!mySeat` 而覆寫狀態列為「請先選擇角色再上傳附件」。
2. **上傳完成後缺少 `renderChatMessages()` 重新渲染，且 `finally` 未清理殘留進度列**：
   - `handleChatFileSelect()` 在寫入 `formal/chat_rooms/{dateStr}/messages/{msgId}` 前呼叫 `setUploadProgress(95)` 繪製 95% 進度卡片。
   - Firebase RTDB `.set()` 會先觸發本機監聽 `chatMessagesHandler`（此時 `chatUploadingItem` 仍為 95%），待 `.set()` 完成將 `chatUploadingItem = null` 後**未再呼叫 `renderChatMessages()`**，導致 95% 進度卡片殘留於 DOM 中直到重新開啟聊天室才被重繪。
   - 此外，早退分支（例如 `renewChatSeatActiveAt()` 失敗）與 `finally` 亦未重繪訊息列表，且連續取消再上傳時 `finally` 可能誤清下一筆上傳的按鈕狀態；同時 `chatUploadingItem.fileSize` 在圖片壓縮後未更新為壓縮後大小。
