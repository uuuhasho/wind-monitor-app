01｜使用 APP 時，資料怎麼流動

以下三條路徑各有不同職責。APP 的手動預報更新直接呼叫 Cloud Run；一般船期及監控操作送到 GAS。

APP 讀取 active_status、schedule_list、daily_records、forecast_data 與 forecast_metadata，並監聽連線及鎖狀態。船期讀取失敗時有 GAS display 備援接口。圖表使用 ECharts，tooltip 依目前選船資料更新。

LINE 進港訊息走另一條路

LINE → Cloud Run /webhook → Gemini 解析 → GAS set_mode → RTDB／船期

Cloud Run 驗證 LINE 簽章，解析並驗證 HH:MM、04:00–17:00，再委託 GAS 查風速、寫入 pob_info、更新船期及嘗試接力。換班接力功能仍在程式中，依使用者決定暫不觀察。

02｜預報更新與工作鎖

輸入與辨識

Cloud Scheduler 或 APP 呼叫 Cloud Run。backend/main.py 取得 RTDB 工作鎖後，先尋找符合日期的本地預報文件，否則從 Gmail IMAP 下載附件；轉為 DOCX、擷取圖片，再用 OpenCV／Tesseract 辨識曲線與起報時間。

起報時間 OCR 不匹配時嘗試 Gemini Vision；並非每次預報都呼叫 Gemini。

融合與發布

backend/src/data_fusion.py 取得 Open-Meteo 陣風，對齊時間與風速單位後融合。透過 rtdb.py 的 ETag 重試機制，把 forecast_data 與 forecast_metadata.updatedAt 一起更新。

原始預報文件解析失敗即停止發布；Open-Meteo 缺資料時對應值可能為空。

到期恢復按鈕，仍由後端保護資料

工作鎖含 owner 與 expiresAt，有效期 300 秒。APP 以 Firebase serverTimeOffset 校正時間，到期後恢復按鈕並重新載入預報；不會因此直接刪除後端鎖。後端發布前再次確認 owner 及有效期，過期工作不能發布；釋放鎖也只限原持有者。每次工作的 runtime/UUID 在 finally 清理。

03｜監控、船期與歸檔

GAS 的資料來源

船期 API／日曆與人工 schedule_overrides 提供船期；港務北堤綠燈塔頁面提供即時風速。GAS 合併資料，更新 RTDB 監控狀態與當日卡片。

setupSystemTriggers 定義每日 04 時船期、每分鐘監控、每日 23 時歸檔，以及日曆變更觸發器；這是程式設定，不代表本次已讀回雲端觸發器清單。

先歸檔成功，再清來源

GAS → Google Sheets 歸檔總表／分類表 → RTDB archive_receipts → 以 ETag 保護刪除 daily_records 來源卡。改期時先建立目標卡並核對收據，失敗保留來源。

Sheets M 欄 archive_id 是對帳與防重複識別，須保留。APP 的 editing_lock 與預報 forecast_update_lock 是不同用途的鎖。

04｜現行部署與資料夾分工

Hosting 發布路徑

frontend → build_hosting.py → public → 原生 PowerShell 暫存 site → Node 逐檔讀取／數量／SHA-256 預檢 → Firebase Hosting。

來源清單與 Firebase 設定放在 site 外，預檢失敗停止；只有 -Deploy 才發布，finally 清理該批暫存。

Cloud Run 與 GAS

backend → deploy_cloud_run.py → ASCII 暫存路徑 → 帶 codex-preflight tag、no-traffic 的 revision → 驗證後再切流量。機密不隨來源打包。

gas 是 Apps Script 來源；push HEAD 與更新 Web App deployment 是兩個步驟，部署需授權。

GitHub Actions：目前 workflow 檔只有手動入口與退役提示，不執行預報；使用者確認遠端已停用。本機 main 是日常工作基準，新增功能另開分支。GitHub 推送與 APP 部署是不同操作。

資料夾詳解請看 專案資料夾架構與清理。backend、frontend、gas 是程式來源；deploy 是部署工具；tests 是隔離測試；runtime 包含備份與查核證據；唯一素材及本機 OCR 資源保留。
